# AGENTS.md

## 1. Цель проекта

Реализовать backend-сервис на Python для проверки дневных и недельных записей наблюдений за детьми с сохранением результатов и истории проверок в PostgreSQL.

Сервис должен предоставлять REST API для:

* загрузки материалов записи;
* определения типа каждого материала;
* проверки комплектности;
* проверки формата и размера файлов;
* формирования итогового статуса проверки;
* сохранения результата в PostgreSQL;
* получения списка и деталей проверок.

## 2. Технологический стек

* Python 3.11

* PostgreSQL
* SQLAlchemy

Управление зависимостями — на выбор:

## 3. Основные принципы

* Код должен быть простым, читаемым и поддерживаемым.
* Следовать стандартным практикам Python и FastAPI.
* Не усложнять архитектуру без необходимости.
* Бизнес-логику отделять от HTTP-слоя и работы с БД.
* Валидацию входных данных выполнять через Pydantic.
* Конфигурацию получать из переменных окружения.
* Не хранить секреты и пароли в коде.
* Использовать типизацию Python.
* Ошибки API должны возвращаться с корректными HTTP-статусами.
* Изменения схемы БД выполнять только через Alembic migrations.
* Не использовать реальные персональные данные детей.
* Ребёнок должен идентифицироваться обезличенным кодом.

## 4. API

### POST `/api/checks`

Принимает:

* `multipart/form-data`;
* `type`: `daily` или `weekly`;
* один или несколько файлов.

После загрузки сервис должен:

1. Провалидировать входные данные.
2. Проверить формат и размер каждого файла.
3. Определить тип материала по имени файла.
4. Проверить комплектность записи.
5. Сформировать список ошибок и предупреждений.
6. Сформировать итоговый статус.
7. Сохранить проверку и её материалы в PostgreSQL.
8. Вернуть результат проверки.

Допустимые типы файлов:

* PDF
* DOCX
* XLSX
* JPG
* PNG

Максимальный размер одного файла: **20 МБ**.

### GET `/api/checks`

Вернуть список всех проверок.

Для каждой проверки вернуть минимум:

* `id`;
* дату;
* тип записи;
* статус;
* количество материалов.

### GET `/api/checks/{id}`

Вернуть полный результат конкретной проверки.

Если проверка не существует — HTTP `404`.

## 5. Типы материалов

Тип материала определяется по имени файла.

Поддерживаемые типы:

| Тип                     | Значение                |
| ----------------------- | ----------------------- |
| Дневник наблюдений      | `observation_diary`     |
| Отчёт о занятии         | `lesson_report`         |
| Обратная связь родителя | `parent_feedback`       |
| Заключение специалиста  | `specialist_conclusion` |

Определение выполняется на основании:

* имени файла;
* паттернов имени;
* количества совпадений.

Если тип определить невозможно:

* не считать файл неизвестным критическим материалом;
* добавить issue уровня `warning`;
* продолжить проверку остальных файлов.

Пример:

`scan_0041.jpg` → warning:

```json
{
  "level": "warning",
  "message": "Не удалось определить тип материала: «scan_0041.jpg»"
}
```

## 6. Комплектность

### `daily`

Обязательные материалы:

* `observation_diary`;
* `lesson_report`;
* `parent_feedback`.

### `weekly`

Обязательные материалы:

* `observation_diary`;
* `lesson_report`;
* `parent_feedback`;
* `specialist_conclusion`.

Отсутствие обязательного материала считается ошибкой уровня `error`.

Пример:

```json
{
  "level": "error",
  "message": "Отсутствует обязательный материал: обратная связь родителя"
}
```

## 7. Проверка файлов

Для каждого загруженного файла проверить:

### Формат

Разрешены только:

```text
PDF
DOCX
XLSX
JPG
PNG
```

Недопустимый формат → `error`.

### Размер

Максимальный размер:

```text
20 MB
```

Файл больше 20 МБ → `error`.

### Имя файла

Если по имени невозможно определить тип материала:

→ `warning`.

Проверки должны выполняться независимо для каждого файла.

## 8. Итоговый статус

Допустимые статусы:

```text
check_in_progress
complete
incomplete
```

Правила:

* `check_in_progress` — проверка выполняется;
* `complete` — отсутствуют ошибки уровня `error`;
* `incomplete` — есть хотя бы одна ошибка уровня `error`.

Warnings не делают запись `incomplete`.

При обычном синхронном выполнении API допускается сразу сохранять конечный статус `complete` или `incomplete`. Статус `check_in_progress` должен быть предусмотрен моделью данных и API как допустимое состояние.

## 9. Формат ответа POST `/api/checks`

Ответ должен содержать структуру, совместимую со следующим примером:

```json
{
  "check_id": "abc123",
  "status": "incomplete",
  "status_label": "Запись неполная — нельзя передавать в анализ",
  "reason": "Отсутствует обратная связь родителя за день.",
  "issues": [
    {
      "level": "error",
      "message": "Отсутствует обязательный материал: обратная связь родителя"
    },
    {
      "level": "warning",
      "message": "Не удалось определить тип материала: «scan_0041.jpg»"
    }
  ],
  "documents": [
    {
      "name": "дневник_наблюдений_15-03.xlsx",
      "detected_type": "observation_diary",
      "size_kb": 142
    }
  ],
  "extracted": {
    "child_code": "Р-014",
    "tutor": "Иванова А. С.",
    "date": "15.03.2025",
    "observed_blocks": "эмоции, коммуникация, поведение, сон"
  },
  "checked_at": "2025-03-15T14:32:00Z"
}
```

`extracted` является демонстрационным результатом. Реализовывать полноценное извлечение содержимого документов не требуется, если это отдельно не предусмотрено заданием.

## 10. История и версии

Необходимо сохранять историю проверок.

Повторная загрузка записи за ту же дату не должна перезаписывать предыдущий результат.

Каждая новая загрузка должна создавать новую версию.

Минимально необходимо хранить:

* идентификатор проверки;
* тип записи;
* дату записи;
* версию;
* статус;
* дату проверки;
* материалы;
* обнаруженные типы материалов;
* ошибки и предупреждения;
* результат проверки.

Предыдущие версии должны оставаться доступными.

## 11. База данных

Использовать PostgreSQL и SQLAlchemy.

Схема БД должна позволять хранить как минимум:

* проверки;
* версии проверок;
* загруженные материалы;
* результаты/issue проверки.

Структуру таблиц выбрать самостоятельно, если она покрывает требования задания.

Все изменения схемы БД оформлять через Alembic.

Не создавать таблицы автоматически при старте приложения вместо миграций.

## 12. HTTP-ошибки

Использовать корректные HTTP-статусы:

* `400 Bad Request` — некорректный запрос/операционные ошибки загрузки;
* `404 Not Found` — ресурс не найден;
* `422 Unprocessable Entity` — ошибка валидации входных данных.

Не возвращать `200 OK` для ошибок API.

Формат ошибок должен быть единообразным.

## 13. Валидация

Использовать Pydantic для:

* параметров API;
* enum значений;
* response schemas;
* структурированных данных результата.

Минимум:

```text
type ∈ {daily, weekly}
status ∈ {check_in_progress, complete, incomplete}
issue.level ∈ {error, warning}
```

1. Определение `observation_diary`.

## 22. Git Workflow

Git используется для фиксации логически завершённых этапов разработки.

### Общие правила

* Не удалять и не переписывать существующую историю Git без явного разрешения.
* Не выполнять `git push` без явного указания пользователя.
* Не использовать `git reset --hard`, `git clean -fd` и другие потенциально разрушительные команды без явного разрешения пользователя.
* Не изменять чужие незакоммиченные изменения.
* Перед началом работы проверить `git status` и учитывать существующие изменения.
* Не коммитить `.env`, секреты, credentials, реальные персональные данные и временные файлы.
* Не делать коммит после каждого отдельного изменения или файла.
* Один commit должен соответствовать одному логически завершённому этапу.

### Порядок работы

Перед изменениями:

```bash
git status
git branch --show-current
```

После реализации этапа:

1. Запустить релевантные тесты.
2. Проверить форматирование и качество кода.
3. Проверить `git diff`.
4. Проверить `git status`.
5. Убедиться, что в commit не попадут секреты и временные файлы.
6. Создать один осмысленный commit.

Пример:

```bash
git add .
git commit -m "feat: implement check validation"
```

### Формат commit message

Использовать Conventional Commits:

```text
feat: ...
fix: ...
test: ...
refactor: ...
docs: ...
chore: ...
```

Примеры:

```text
chore: initialize project
feat: add checks API
feat: implement material detection
feat: add completeness validation
feat: persist checks in PostgreSQL
test: cover check validation
docs: add project documentation
chore: add Docker Compose setup
```

### Этапы разработки

Предпочтительно фиксировать работу примерно такими коммитами:

1. `chore: initialize project`
2. `chore: add Docker Compose and PostgreSQL`
3. `feat: add database models and migrations`
4. `feat: implement material detection`
5. `feat: implement check validation`
6. `feat: add checks API`
7. `feat: add check history`
8. `test: cover validation logic`
9. `docs: add README`

Количество и названия коммитов можно изменить, если фактическая структура работы отличается.

### Push

Агент не должен выполнять:

```bash
git push
```

без явного указания пользователя.

После завершения этапа агент должен сообщить:

* что реализовано;
* какие тесты пройдены;
* какой commit создан;
* краткий результат `git status`.

Публикация изменений выполняется пользователем либо только после его явного подтверждения.
